OBSERVACIÓN
-----------
- Transporte ADB (LADB): localhost:38639 -> estado "device" (sin PC)
- Identidad shell adb: uid=2000(shell) gid=2000(shell) context=u:r:shell:s0
- Starter: /data/local/tmp/shizuku (16.680 bytes, ejecutable, prop. shell)
- Servidor: shizuku_server UP, PID 12057, usuario shell
- rish: ~/bin/rish + rish_shizuku.dex (kit exportado), patrón: rish -c "cmd"
- Contexto previo: demo manual 2026-09-12 (ciclo 5704 -> 12057); al iniciar
  este PoC el server seguía vivo con el PID 12057.

HIPÓTESIS
---------
Si shizuku_server muere, un shell UID 2000 alcanzable desde LADB puede
relanzarlo ejecutando el starter nativo /data/local/tmp/shizuku, SIN PC,
SIN root y SIN tocar app_process/CLASSPATH. El éxito solo es demostrable
con evidencia mecánica (proceso nuevo, PID distinto, estable en el tiempo)
MÁS una prueba funcional post-recuperación vía rish.

ACCIÓN
------
1. Crear ~/ladb-shizuku-recovery/ con 3 scripts POSIX autónomos:
   - doctor.sh  : 5 chequeos en cadena (adb client -> transporte con serial
                  dinámico -> uid 2000 -> starter -> server + prueba rish)
                  exit: 0=UP · 1=DOWN/transporte · 2=DEGRADED
   - recover.sh : si DOWN, lanza starter vía adb (nohup, background);
                  estabilidad N0/N1/N2/N3 (mismo PID), pid-change (nuevo=OLD),
                  prueba funcional rish -c "id". Idempotente.
   - verify.sh  : server presente + prueba rish
                  exit: 0=UP+FUNCTIONAL · 1=DOWN · 2=UP pero rish bloqueado
2. doctor.sh -> server UP -> rama DOWN no aplicaba de inicio.
3. Con aprobación explícita del usuario: ciclo forzado:
   rish -c "kill -9 12057" (solo vía rish; adb UID 2000 no puede)
   -> confirmación de ausencia por ps -> recover.sh -> verify.sh
4. Evidencia registrada en ~/ladb-shizuku-recovery/{evidence.txt,oldpid.txt}

NOTAS DE OPERACIÓN
------------------
1. rish exige RISH_APPLICATION_ID y MANAGER_APPLICATION_ID en el entorno;
   sin ellas aborta sin ejecutar nada (ocurrió en el primer intento).
2. El exit 255 de rish tras matar el server NO es un fallo: el transporte
   muere con el servidor. La verdad de ground es ps, no el exit code.
3. adb shell (UID 2000) no puede matar al server (uid distinto):
   matar solo vía rish.
4. El puerto de LADB (38639) puede cambiar si LADB se reinicia (fallback
   observado antes: 37685). Los scripts detectan el serial dinámicamente.
5. Patrón del kit rish exportado: siempre "rish -c \"cmd\""; sin -c el
   server trata el comando como path y muere con exit 127.
